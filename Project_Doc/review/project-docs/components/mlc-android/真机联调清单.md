# App 本地 AI 真机联调清单

本文档仅用于 Android 自定义基座联调。

适用范围：

- `helpsupport-frontend`
- `App` 本地模式
- `UTS + local-llm-bridge + mlc4j`

不在本文档范围内：

- iOS 原生运行时接入
- iOS 离线推理验收

## 1. 目标状态

联调通过后，至少应满足：

1. App 本地模型页能识别到原生桥接。
2. App 本地模型页能识别到 `MLC` 运行时资产。
3. App 本地模型页能识别到 `JSONFFIEngine` 可用。
4. 模型下载完成后，可进入本地聊天页。
5. 本地模式消息不走服务端，只存本地会话与本地记录。

## 2. 前置条件

联调前先确认：

1. 使用 Android 真机，不要只看 `uni build -p app-android` 的前端构建结果。
2. 使用 HBuilderX 自定义基座或等价原生工程，且基座已包含 `local-llm-bridge`。
3. 已准备 `mlc_llm` 环境，可执行 `mlc_llm package`。
4. 已安装 Android NDK，且 `pnpm check:app-local-ai -- --skip-build` 能通过 `Android NDK / TVM_NDK_CC` 检查。
5. 已生成项目模型打包配置：

```bash
pnpm generate:mlc-config
```

## 3. 运行时资产准备

### 3.1 打包 `mlc4j`

在 `helpsupport-frontend` 目录执行：

```bash
pnpm package:mlc-android-runtime
```

打包成功后，应拿到 `dist/lib/mlc4j`。

### 3.2 同步到 UTS Android 插件

```bash
pnpm prepare:mlc-android-runtime -- --source <dist/lib/mlc4j目录>
```

如需重置已经同步到插件目录的运行时资产，可先执行：

```bash
pnpm clean:mlc-android-runtime
```

### 3.3 同步后自检

```bash
pnpm check:mlc-android-runtime
```

如果这条命令失败，优先先修复运行时资产，再继续自定义基座和真机联调。

如果你切换了 `mlc_llm` 版本、ABI 或重新打了一轮 `mlc4j`，建议使用下面的顺序避免旧资产残留：

```bash
pnpm clean:mlc-android-runtime
pnpm prepare:mlc-android-runtime -- --source <dist/lib/mlc4j目录>
pnpm check:mlc-android-runtime
```

### 3.4 联调前体检

```bash
pnpm check:app-local-ai
```

如果只想跳过构建，先看环境和运行时资产状态，可执行：

```bash
pnpm check:app-local-ai -- --skip-build
```

如果体检里 `Android NDK / TVM_NDK_CC` 失败，先处理这个问题，不要继续跑 `pnpm package:mlc-android-runtime`。当前脚本会优先从 `TVM_NDK_CC`、`ANDROID_NDK_HOME` / `NDK_HOME`、`ANDROID_SDK_ROOT` / `ANDROID_HOME` / `~/Library/Android/sdk` 自动解析 NDK；如果都失败，说明当前机器还没有安装可用的 NDK。

如果体检里 `MLC 源码依赖` 失败，说明本地 `.mlc-llm-source` 子模块不完整。至少要补齐 `3rdparty/tvm`、`3rdparty/tokenizers-cpp` 和 `3rdparty/xgrammar`，可在 `.mlc-llm-source` 目录执行：

```bash
git submodule update --init --recursive
```

如果体检里 `Android 绑定构建工具` 失败，说明当前机器缺少 `rustup/cargo/rustc`、`cmake` 或 `java`。`mlc4j` 打包阶段会直接依赖这套工具链。

如果已连接 Android 真机，还建议先做一次设备侧预检：

```bash
pnpm check:app-local-ai-adb -- --device <serial>
```

这条命令会检查：

1. 当前 `adb` 是否可用
2. 在线设备列表和目标设备序列号
3. 设备 ABI 是否与当前 `arm64-v8a` 运行时匹配
4. `UniApp AppID` 是否能从设备侧 `Android/data/*/apps/<appid>` 反查出候选包名
5. 若已传 `--package`，或只识别出 1 个候选包名，则继续检查安装状态和包信息
6. 包的 `versionCode / versionName / nativeLibraryDir`
7. 常见 `_doc/help-local-llm` 目录是否已出现

如果你已经知道自定义基座包名，也可以直接执行：

```bash
pnpm check:app-local-ai-adb -- --device <serial> --package <包名>
```

如果准备开始点模型、发消息，建议同时开一条原生日志窗口：

```bash
pnpm logcat:app-local-ai -- --device <serial> --clear
```

如果需要直接看设备侧模型目录是否完整，可执行：

```bash
pnpm check:app-local-ai-device-models -- --device <serial>
```

这条命令会逐个检查 `_doc/help-local-llm` 下的本地模型目录，输出：

1. 模型目录是否存在
2. `bridge-meta.json` 是否存在且可解析
3. `mlc-chat-config.json` / `tensor-cache.json` 是否存在
4. tokenizer 文件和参数分片是否齐全
5. 每个模型缺失的具体文件

如果需要把预检、自检和 `logcat -d` 一次性打包成一份报告，可执行：

```bash
pnpm collect:app-local-ai-device-report -- --device <serial>
```

默认会在 `mlc-android/reports/` 下生成一份带时间戳的 Markdown 报告和同名 JSON 摘要。

如果需要把采集结果快速转成“多设备联调汇总表”建议行，可执行：

```bash
pnpm summarize:app-local-ai-device-report -- --latest
```

如果需要基于最新采集摘要自动生成一份“单机联调记录”预填初稿，可执行：

```bash
pnpm prefill:app-local-ai-device-record -- --latest
```

如果希望把采集、预填记录、汇总建议行和索引一次性全部生成，可执行：

```bash
pnpm finalize:app-local-ai-device-report -- --device <serial>
```

如果希望把最新一份摘要结果直接落到 `多设备联调汇总表.md`，可执行：

```bash
pnpm sync:app-local-ai-summary-table -- --latest
```

如果希望把页面诊断结果继续同步回项目根目录的专项测试材料，并同时更新 `AI本地能力首轮验证记录.md` 与 `功能测试清单.md`，可执行：

```bash
pnpm sync:app-local-ai-root-docs -- --json <摘要路径>
```

执行后会默认在摘要同目录生成一份 `.root-docs-sync.md` 回填报告，便于留档和复核。

如果希望在总装时一并同步汇总表，可执行：

```bash
pnpm finalize:app-local-ai-device-report -- --device <serial> --sync-table
```

如果你已经在页面点了“复制联调信息”，建议把文本保存后再执行：

```bash
pnpm finalize:app-local-ai-device-report -- --device <serial> --diagnostics-input <联调信息文本路径> --sync-table
```

这样生成的摘要、预填记录和汇总表行会直接带上 `nativeBridgeDetected / packagedRuntimeDetected / runtimeReady` 三项结果。

如果你还希望在总装结束后，把 `APP-LOCAL-01` 到 `APP-LOCAL-04` 以及根目录结论文档一并回填，可执行：

```bash
pnpm finalize:app-local-ai-device-report -- --device <serial> --diagnostics-input <联调信息文本路径> --sync-table --sync-root-docs
```

总装成功后，产物目录里会额外多一份 `.root-docs-sync.md`，用于记录本次根目录文档回填内容。

推荐做法：

1. 先执行一次 `--clear`
2. 再进入本地模型页点击“刷新”
3. 再执行模型下载、模型修复、进入本地模式、发送首条消息
4. 观察 `HelpLocalLLM` 是否输出“初始化运行时”“加载模型”“开始本地推理”“本地推理完成”等日志

同步完成后，至少检查这些文件：

- `uni_modules/local-llm-bridge/utssdk/app-android/assets/mlc-app-config.json`
- `uni_modules/local-llm-bridge/utssdk/app-android/libs/*.jar`
- `uni_modules/local-llm-bridge/utssdk/app-android/libs/<abi>/*.so`
- `uni_modules/local-llm-bridge/utssdk/app-android/.mlc-runtime-manifest.json`
- `uni_modules/local-llm-bridge/utssdk/app-android/config.json`

## 4. 构建前核对项

在提交到自定义基座前，建议先跑：

```bash
pnpm type-check
pnpm build:h5
pnpm build:app-android
```

如果这三条命令都通过，说明前端、`UTS` 导出和 App 构建链没有被当前改动破坏。

## 5. 真机联调入口

打开 App 后进入：

- `聊天 -> 本地模式 -> 本地模型`

页面顶部会出现“App 本地推理状态”卡片。

当前卡片会显示三类信息：

- 是否检测到原生桥接
- 是否检测到 `MLC` 运行时资产
- `JSONFFIEngine` 是否就绪
- App 私有目录模型根路径
- 每个已准备模型的目录状态（`bundle` 是否完整、`Marker` 是否存在）
- 缺失文件明细（例如缺少 `mlc-chat-config.json`、`tensor-cache.json` 或某个 `params_shard_*.bin`）

当前卡片还支持两个联调动作：

- 点击“刷新”可重新拉取当前基座的桥接状态
- 点击“复制联调信息”可一次性复制设备信息、桥接状态、当前激活模型、可用模型和待修复模型，便于贴到联调记录里

模型卡片也有目录状态提示：

- 如果显示“待修复”，说明前端状态认为模型已下载，但 App 私有目录里仍缺关键文件
- 待修复模型会继续显示在“已下载”列表里，便于直接修复或删除，不会被误判成普通“未下载”
- 此时直接点击该模型卡片会走“修复下载”，优先补齐缺失文件，不需要先删再重下
- 如果当前激活模型处于“待修复”，页面底部“进入本地模式”按钮会禁用，并提示先修复模型

## 6. 诊断结果解释

### 6.1 未检测到原生本地推理桥接

表现：

- `nativeBridgeDetected = false`
- 文案提示“当前基座未检测到原生本地推理桥接”

优先检查：

1. 是否使用了自定义基座，而不是普通调试基座。
2. `uni_modules/local-llm-bridge` 是否已进入当前 App 工程。
3. 基座里是否能拿到 `uni.requireNativePlugin('local-llm-bridge')`。

### 6.2 已检测到桥接，但未检测到 MLC 运行时资产

表现：

- `nativeBridgeDetected = true`
- `packagedRuntimeDetected = false`

优先检查：

1. 是否已执行 `mlc_llm package`。
2. 是否已执行 `pnpm prepare:mlc-android-runtime -- --source <dist/lib/mlc4j目录>`。
3. `assets/mlc-app-config.json` 是否已同步到 `utssdk/app-android/assets/`。
4. `mlc-app-config.json` 中是否已有 `model_lib`。

### 6.3 已检测到运行时资产，但 JSONFFIEngine 未就绪

表现：

- `packagedRuntimeDetected = true`
- `runtimeReady = false`

优先检查：

1. `libs/*.jar` 是否已同步。
2. `libs/<abi>/*.so` 是否与真机 ABI 匹配。
3. `config.json` 中 `abis` 是否包含当前设备架构。
4. 自定义基座打包时是否把 `jar/so` 实际带入了原生工程。

### 6.4 运行时完全就绪

表现：

- `nativeBridgeDetected = true`
- `packagedRuntimeDetected = true`
- `runtimeReady = true`

下一步直接做：

1. 下载一个本地模型。
2. 进入本地聊天。
3. 连续发 2 到 3 条消息。
4. 返回首页检查最近聊天。
5. 退出重进 App 后检查本地会话是否仍在。

## 7. 联调冒烟清单

建议按这个顺序验证：

1. 本地模型页显示“原生桥接已检测到”。
2. 本地模型页显示“已检测到 MLC 运行时资产”。
3. 本地模型页显示“JSONFFIEngine 可用”。
4. 下载一个小模型，下载成功后状态变为“已下载”。
5. 切换激活模型成功。
6. 进入本地模式聊天页，发送消息后可返回结果。
7. 切到最近聊天，能看到本地会话。
8. 删除本地模型后，模型目录与本地状态都同步清理。

## 9. 已知边界

当前代码仍有这些边界：

1. `uni build -p app-android` 只能说明前端和 `UTS` 编译链通过，不等于原生资产已经真正在真机可用。
2. 当前 `onToken` 仍然是整段结果回填，不是逐 token 刷新。
3. `interrupt()` 目前仍是“销毁并重建 runtime”的做法，不是底层更细粒度的中断。
4. iOS 端还没有同等程度的原生推理接入，不应按 Android 相同标准验收。
